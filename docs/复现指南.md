## 当前适用范围

本指南用于D1–D2旧LED/RC基础链路，不支持任意电路或ESP32-S3目标整板。**这是链路验证版本，不是可直接生产的设计。**

2026-10-25 BASE-01只证明本机独立目录：本地27/27、上游121/121、六步复现通过，双模板真实客户端回读与截图成功。源码清单SHA256为 `7F330A1E672FEDE8BEF7C34B31BAB516C61C09185B936CE3213F3FB1E0A43653`。BASE历史验证时的HEAD为 `a031dae`，当时存在必要未跟踪源码；该提交不能单独定位BASE快照。本次同步已纳入核心复现所需文件，执行前用 `git rev-parse HEAD` 记录实际同步版本。

## 准备环境与运行

Node.js 18+，顶层核心链路无第三方npm依赖；BASE实际版本为Node24.21.0/npm11.19.0。Git用于取得明确版本；解压候选源码无需伪造.git或commit。独立vendor格式工具另有依赖，不属于核心复现入口。

在候选根目录执行：

```powershell
node scripts/reproduce.js
```

或显式指定新日志目录：

```powershell
node scripts/reproduce.js --out logs/baseline
```

这会依次执行本地测试、上游smoke、LED生成/校验、RC生成/校验。默认生成会覆盖候选目录下的 `dist/`，请在可丢弃候选中执行，并保留需留存的旧产物。预期最终为 `6 通过 / 0 已知问题 / 0 失败 / 0 跳过`；每步命令/实际退出码和stdout/stderr应完整保留，不能只交成功截图。

也可单独运行 `npm test`。若从公开仓库取得源码，应先核对交付说明列出的实际commit与清单，不能只执行clone并默认版本一致。

## 桌面客户端与电气检查

有LCEDA Pro V4.1+时，设置 `LCEDA_CLI` 为你实际的可执行文件路径，再串行运行 `npm run verify:client`。结果在各模板 `verification/` 下，包括result.json及原理图/PCB截图。该命令会重生成模板及管理客户端会话，不要与其他客户端任务同时运行。

`node scripts/reproduce.js --with-client` 额外执行 `scripts/audit.js`，这是电气/BOM审计，与回读检查不同。当前脚本对审计exit1可以记为warn，不计基础生成失败，因此总exit0不等于DRC通过。最新已知结果是原理图ATTRMATCHCODE、PCB Netlist Error；PCB原始违规在Errors分组，不能按摘要缺字段推定warning。

RC临时副本的官方同步实验重开后PCB DRC通过，但原候选未修复；保存格式导致原版validate异常。隔离补丁未接入，详见[Issue #2](https://github.com/easyeda/easyeda-eprj3-skill/issues/2)和[中文补充](https://github.com/easyeda/easyeda-eprj3-skill/issues/2#issuecomment-6396044559)。Device UUID差异不是已证明的唯一根因，也不把旧W3计划当作已实施路线。

## Docker 配置与尚未验证项

Docker只面向六步基础复现，不包含桌面客户端、DRC审计或全部辅助npm命令。Dockerfile使用明确COPY；.dockerignore默认排除再按白名单放行核心输入，不复制客户任务书、docs/repro实验副本、插件、固件SDK/build、资料库下载和既有dist/logs。

当前仅静态检查上下文和核心源文件闭包；本轮只读探测未找到Docker命令，没有安装、构建或运行容器。以下是待验证操作，不是已通过证据：

```text
docker build -t hardware-generator .
docker run --rm hardware-generator
```

镜像基于Node20 Alpine；BASE实测是Windows Node24，不能据此保证Linux tar打包、ZIP格式或其他跨平台行为。若Docker运行失败，保留实际错误；需要改业务脚本时另行报告，不绕过校验。容器内无.git，summary的commit可能为null，需同时归档输入源码清单。

“Docker/依赖”按任务书原文交付，不由本指南擅自展开成Docker与全新物理电脑都必须分别通过。已有依赖方式实跑、容器未验证、第三方环境未验证，必须分别如实写明。

## 如何补足他人干净环境证据

请使用已固定、包含全部必要未跟踪源码的候选，让另一位操作者在隔离且不依赖原工作区的环境运行。记录候选身份、操作人/独立性、Node/npm/系统版本、完整命令和退出码、summary与每步日志。若有客户端再单独记录其版本与解析证据。不要公开个人目录或客户资料。

任何一份本机summary只能证明那一次执行，不能单独证明“他人可运行”。客户接收或验收认可也需单独回执；不把技术日志等同客户确认。

## 常见问题

|现象|检查方式|
|---|---|
|Node24报Cannot find module目录|使用reproduce.js或显式列文件的npm test|
|客户端报Cannot find module|检查ELECTRON_RUN_AS_NODE；可清除此变量后在独立会话复测|
|SESSION_NOT_FOUND或SERVER_SHUTTING_DOWN|保留首次日志，协调串行会话；本轮成功不能证明历史根因已修复|
|工程目录改名后找不到索引|目录basename必须等于项目名|
|没有docs/repro原始日志|它是本地排除目录；正式交付另提供已审阅脱敏摘要，不能把缺文件当通过|
